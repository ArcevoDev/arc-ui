# architecture

- Prefers clean directory scaffolding: empty stub directories that serve no purpose should be flagged and either populated or removed; every directory should have intentional content. Confidence: 0.85
- Prefers domain-namespaced subdirectory organization (e.g., `forms/auth/`, `forms/mfa/`) with barrel exports resolving upward to a root barrel, keeping related files grouped by domain rather than flat. Confidence: 0.8
- Uses barrel exports (index.ts re-exports) for grouped directories to improve import readability and provide clean public API surfaces. Confidence: 0.85
- Prefers splitting large files (200-300+ lines) into smaller, focused modules extracted by concern, for future-proof maintainability and independent testability. Confidence: 0.85
- Auth components must be domain-customizable (different configs for fintech vs med vs edu): not one-size-fits-all. Confidence: 0.85
- Include a welcoming landing page and deployed documentation site alongside the component library. Confidence: 0.70
- Landing page must have real routed pages with actual content (components gallery with live demos, docs/design-tokens, theming, changelog) instead of dummy/placeholder sections and fake nav links: stacked one-page sections with routes that don't exist are flagged as a gap, not acceptable for a public site. Confidence: 0.6
- Interested in modern micro-interaction and visual polish (gradient text, typing animation, smooth scrolling, hover/micro-interactions) as UI enhancements for the landing/marketing surface: welcomed as post-release polish items, not release blockers. Confidence: 0.6
- Prioritize component development by developer-time-saved: build what takes devs the most effort to implement (navbar variants, sidebars, notification drawers, etc.) over visually flashy additions. Value-to-effort ratio is the primary selection criterion for new components. Confidence: 0.8
- Ship functional components first, defer animations and visual polish until after the first public release: "beautifying" is a post-launch activity, not a pre-launch blocker. Animation and visual decoration should not delay the initial public package. Confidence: 0.85
- Prefers a custom-built component showcase/docs site (with live previews, props tables, code copy, search) as the public documentation surface over exposing raw Storybook: Storybook remains an internal dev tool. Modern UI systems (shadcn/ui, Chakra, Radix) are the reference for how the public site should look and feel. Confidence: 0.65
- Prefers lucide-react icons over emoji characters on landing pages and marketing surfaces: emoji in feature cards or navigation looks unprofessional on a public-facing site; lucide provides consistent, scalable vector icons. Confidence: 0.8
- Landing page must present as a general-purpose open-source component library (like shadcn/ui, Radix, PrimeReact): not as an internal ecosystem tool. Copy, badges, and messaging should appeal to external developers and describe general value props, not internal repo consolidation or org-specific tooling. Confidence: 0.8
- Dogfood the library's own components on the landing/marketing page to validate real-world rendering and prove components work in a real app context: the landing page is a first-hand testing surface, not just a marketing page. Confidence: 0.8
- Provide a sandbox, playground, or interactive sample space (within Storybook or alongside it) where all components can be explored, demoed, and tested: not just documented in isolation. Confidence: 0.75
- Build a differentiated component library wired to arc-id SDK, not a generic clone of existing UI libraries. Confidence: 0.65
- Prefers npm package installation as the primary consumption model for UI libraries (install and import directly like react-email), with CLI component init (like shadcn add) deferred as a secondary tier. Confidence: 0.8
- Prefers publishing packages as public on npm (not private/internal), using changesets for versioning/changelogs and a CI/CD pipeline with GitHub Actions. Confidence: 0.8
- Uses Storybook as the development preview environment for testing and validating components before deployment. Confidence: 0.8
- TypeScript type declarations (e.g., `vite-env.d.ts` with `/// <reference types="vite/client" />`) must exist in EVERY directory that contains files importing non-TS assets (CSS, images, etc.), not just `src/`: Storybook config files in `.storybook/` import CSS and must have their own declaration file to avoid IDE type errors. Confidence: 0.7
- Uses MDX documentation pages (getting-started, contributing, design-tokens, theming, auth-guide) alongside component stories in Storybook, and expects them to compile in production builds: not just in dev server mode. Requires explicit `@storybook/addon-docs` configuration with Vite 8 compatibility adjustments for production. Confidence: 0.75
- Keeps `tsconfig.json` project references synchronized with actual directory structure: stale references to nonexistent directories must be removed to prevent build toolchain (rolldown resolver) failures. Confidence: 0.65
- When fixing a reported issue, perform a comprehensive cross-repo gap analysis: audit ALL sibling repos (arc-id, arcbase, arc-wallet) to identify and close every related gap, not just the immediately reported issue. Single-issue fixes are incomplete; a full gap matrix across all consuming repos is expected, and gaps identified in docs must be closed once and for all. Confidence: 0.9
- Storybook is the verification surface for visual fidelity: components aren't "done" just because they typecheck; they must also render with proper styling (colors, spacing, layout) in the dev preview. Confidence: 0.85
- Prefers a framework-agnostic, composable layout shell (slot-based: <Shell sidebar topbar>content</Shell>) that consumers wire their own routing into: not a framework-coupled layout. Confidence: 0.7
- Prefers using the latest stable major versions of core dependencies and tools (e.g., Tailwind CSS v4 with Rust parser) rather than falling behind on major releases. Confidence: 0.7
- Prefers centralized shared configuration and design tokens at the monorepo-root or shared-package level, not duplicated per app: each app should only hold per-entrypoint wiring (e.g., Vite plugin instantiation), not shared config. Confidence: 0.65
- Design packages for unknown 3rd-party consumption: API surfaces, configurability, and docs must serve developers who have no knowledge of internal arc-ecosystem conventions; not just internal reuse across company repos. Confidence: 0.8
- Before designing a shared abstraction package (e.g., layout), audit all consuming repos (arc-id, arcbase, arc-wallet) to find true shared patterns and avoid premature abstraction. Confidence: 0.7
- Rejects `as unknown as never` and similar type-coercion hacks: type safety is non-negotiable; dead type escapes must be removed in favor of honest optional typing. Confidence: 0.9
- Shared packages within the monorepo must consume other sibling shared packages (e.g., auth package uses the components package's Button, Dialog, etc.) rather than duplicating UI patterns or rolling custom raw elements: diversion from this dependency chain is flagged as a problem. Confidence: 0.7
- The component library should be icon-library-agnostic: icons must be accepted as props or slots, not hardcoded, so consumers can wire in their icon library of choice (lucide, react-icons, etc.) without being forced into a vendor lock-in. The library should not ship its own icon set. Confidence: 0.7
- Domain presets/templates should be icon-library-agnostic: they express domain structure (href, label, badges), not visual wiring. Consumers bring their own icon library; presets don't import or fake icon dependencies. Confidence: 0.85
- README is a primary documentation surface, not a placeholder: must include a full packages table with status, quick-start code example, architecture explanation, and consumption model. Confidence: 0.85
- Uses Tailwind CSS v4 with a shadcn-style theme (CSS custom properties mapped to utility classes like `bg-background`, `text-foreground`) as the styling approach for the UI component library. Confidence: 0.9
- Typography must be explicitly configured in the Tailwind v4 `@theme` block: `--font-sans` must map to the project's actual body font (e.g., Inter via `--font-body`), and `--font-mono` to the code font (e.g., JetBrains Mono); relying on Tailwind v4's system-ui defaults results in visually unacceptable rendering that the user flags as "ugly." Confidence: 0.85
- Visual quality is verified by inspecting the rendered output in a browser, not by build success alone: the user calls out when "everything looks the same" (components lack styled differentiation) or fonts appear ugly; checking that the CSS toolchain ran is insufficient without confirming the actual visual result meets a polish bar. Confidence: 0.85
- Styling pipeline (Tailwind config + PostCSS + stylesheet with @tailwind directives) must be fully wired before components can be considered functional: bare utility classes without a working CSS toolchain are invisible styling debt. Confidence: 0.85
- When using Tailwind v4 in a pnpm workspace monorepo, the Rust-based scanner does not automatically crawl compiled workspace dependency sources for class names; explicit `@source` directives pointing to each workspace package's `src/` directory are required in the consuming app's entry CSS so utility classes used in shared component packages are generated in the final bundle. Confidence: 0.8

- Components should support icon-flexible variants: e.g., a badge that works with an optional icon, including an icon-only badge; icons optional by default rather than required. Confidence: 0.65
- The library should ship theme support: a theme toggle component and runtime-switchable themes customizable per consumer preference, exposed on the landing page so layouts can switch themes. Confidence: 0.7
- All components must have their tests wired as part of completion: unwired test coverage across the component set is a flagged gap, not an acceptable state. Confidence: 0.6
- Prefers the modern "pill" navbar aesthetic used by current software: a floating rounded bar with frosted-glass backdrop blur (content scrolling behind it appears blurred/translucent), with a segmented link tray and active chip — over classic full-width sticky bars, including on marketing/landing pages. Confidence: 0.7
- Layout shells should ship as two responsive variants: (1) a full sidebar with labels, and (2) a sidebar collapsible to an icon-only rail with tooltips — both must be screen responsive (e.g., collapsing to a mobile sheet), with the collapsed choice persisted. Confidence: 0.7
- Component and layout names must unambiguously reveal their purpose: a generic name for a specialized shell (e.g., AppLayout that is really an auth page shell) is misleading and should be renamed to something explicit (e.g., AuthLayout), keeping a deprecated alias for backwards compatibility. Confidence: 0.75
- All components — auth included — must be dynamically customizable by consumers through prop families: `appearance` (className overrides), `slots` (content replacement), and `config` (Partial config/behavior overrides). Presets should be plain objects consumers can spread and extend per-instance. Confidence: 0.8
- Navbar variants must be full-featured, not reduced: the pill variant must support actions, badges, and sub-links (dropdowns) exactly like other variants; a variant is not a stripped-down version. Confidence: 0.6
- Prioritizes speed to the initial npm publish: check tracker validity, resolve publish-blocking issues, and publish ASAP rather than accumulating more features, variants, or polish before the first release. Confidence: 0.6
- Proactively removes deprecated API usage: deprecated aliases (e.g., React.ElementRef → React.ComponentRef, z.string().email() → z.email()) must be replaced with the modern non-deprecated form, following the pattern already standardized across the rest of the codebase (confirmed from other components) rather than inventing a new one. Confidence: 0.8
- Requests an explicit codebase-solidity assessment for both internal and external use before release: expects a go/no-go verdict that calls out concrete blockers and known gaps (e.g., npm auth, uncommitted changes, broken lint), not just a green build/test run. Confidence: 0.6
- Config files should be kept minimal and conservative: speculative workaround plugins/filters in build configs (e.g., unshifting a `react()` babel transform, extra `vite:*` filters added to "fix" a dev-mode hang) are reverted in favor of the known-good committed config; only harmless improvements (e.g., `chunkSizeWarningLimit`) are kept. Experimental config churn that doesn't fix the problem adds risk to a working build. Confidence: 0.65
